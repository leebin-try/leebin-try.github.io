**核心判断：工程智能体必须先有可评分的执行环境，才谈得上比较能力。目前只验证了 CUDA 模型推理，完整 Docker 任务链未建立，没有官方得分；继续改提示词无法补上这个环境缺口。**

## 问题定位：评分对象包含一个可以执行的世界

工程智能体交付的可能是代码、设计文件或其他可读产物，质量由任务环境里的评分器决定。模型回复只是中间过程，任务文件、工具、运行依赖和产物位置共同规定了“完成”的含义。这与一张固定 CSV 的预测接口差别很大。

因此，至少要分清四层：模型服务能否响应、智能体是否正确调用工具、任务宿主是否能提供所需环境、评分器是否能读取最终文件。某一层可用不能推出其余三层也可用；把它们合并成“agent 已经跑通”会使后续排障失去对象。

这里的缺口是完整 Docker 任务环境。它不等于模型质量低，也不等于已经得到一个零分结果。对尚未完成的项目，最专业的材料应是清楚的系统边界图与可执行验收条件，而不是一张没有真实任务支持的能力曲线。

## 技术思路与路线

**路线概览：**固定任务与输入 → 建立 Docker 宿主和工具桥接 → 智能体读写交付文件 → 评分器读取同一产物 → 保留任务评分与环境证据。目前停在完整任务环境准入之前。

### 系统边界：模型、工具与任务环境

官方模板通过任务桥接层连接 Docker 任务环境，模型和工具由 Pi harness 协调。一个任务的文件、容器、执行权限、交付路径和评分器共同构成评测对象。单独替换模型或调整提示词，不能替代这些条件。

已完成的远程探针在 T4 环境上运行过小型 Qwen 模型，验证了 CUDA 推理。模型只使用了一个 GPU；这不是完整工程任务，也不是双 GPU 工程能力评测。

### 实现展开：把一次工程任务做成可审计的事务

一个最小任务事务可以写成：获得固定输入与版本，建立隔离工作目录，启动工具可达的任务容器，让智能体读取任务并写产物，再让评分器在声明的上下文里读取它。每个阶段应记录开始、结束、错误类型和产物位置。

```text
输入快照 → 宿主／容器就绪 → agent 执行
                              ↓
评分记录 ← grader 读取产物 ← 校验交付位置
```

若工具调用返回“成功”，还要检查工具实际写出的文件是否位于评分器会读取的位置。若模型返回了解释，却没有生成文件，应该归入交付失败；若评分器本身没有启动，则不能把它与一个被真实评分器判错的答案混为一谈。

已做过的 GPU 探针验证小模型在 CUDA 上能响应，没有测到这个事务的后半段。它适合证实模型服务路径，无法用于估计工程任务解决率，也不能替代 Docker 权限、daemon、挂载和命名空间的验收。

## 评价方式

本题的最终评价对象是任务交付物，按官方评分器的任务规则判定，不能用对话是否流畅或模型能否调用 CUDA 替代。一个有效评测至少同时具备固定任务版本、可执行环境、可定位交付物和评分器终态。

当前没有满足这些条件的完整任务结果，因此无分数可比较。环境检查要报告依赖、权限与桥接是否可用；能力检查则在环境验收后报告任务结果。前者失败，不等于后者已经测得零分。下面的验收标准属于后续设计。

### 怎样让下一步有明确的通过与失败

我会先选择一个最小、公开且有现成评分器的开发任务，固定任务版本，要求独立复现三件事：容器可从相同输入启动；产物能穿过工具工作目录进入交付目录；评分器对一个已知合法样例给出预期结果。只有这三件事成立，才值得比较模型或提示词。

这不是用合成成功替代真实能力验证。已知样例只是验收评测线路，随后还要在真正未解决任务上检验 agent。区分线路验收与能力检验，可以避免用一条“模型能说 OK”反复证明一个从未被测量的能力。

这项工作目前最可迁移的内容，是环境缺口清单和错误归属，而不是某种模型排名。遇到浏览器、CAD、仿真、机器人或容器任务时，先把完整评分事务画出来，常常能提前发现根本无法在当前宿主里满足的约束。

## 结果与证据

### 为什么没有继续用“先跑一点”掩盖问题

当时的 Kaggle 环境缺少 Docker 执行文件、daemon socket 和所需能力，非特权命名空间也未建立出可用路径。在零付费支出的约束下，没有得到合适的完整 Docker 宿主环境。

因此，目前没有完整公开开发任务的评分，没有可确认的官方 Writeup 评估结果，也没有官方比赛得分。仓库、静态检查和模型回复都真实存在，但它们回答的是别的问题。

## 思考与结论

**结论：**这次工作定位了系统边界上的阻塞，尚未建立模型优劣证据。专业结论应停在“完整评测不可用”，而非把小模型响应、GPU 分配或计划中的任务数当作完成比赛。

### 观点：评测基础设施本身应有验收标准

对普通分类器，一份输入表和标签就能开始离线验证；对工程智能体，环境行为也是问题定义的一部分。环境不一致时，即便产生了答案，也可能根本无法与官方结果比较。

我倾向于把验收拆成三个问题：任务能否在隔离环境里启动；智能体能否读取输入并把产物放到正确位置；评分器能否真正读取产物并产生结果。只有最后一环走通，才进入模型能力比较。

### 可迁移的经验

这个案例适合提醒所有带浏览器、容器、游戏或工具执行的任务：先证明评测闭环，再投入大模型调参。下一步应是获得合适且已授权的远程 Docker 环境，运行真实开发任务并保留产物与评分日志。在这之前，把状态留为“验证受阻”本身就是必要的工程结论。

## 下一步

以下是按优先级排列的后续实验设计，尚未执行；通过条件与比较口径应在运行前固定。

1. 先用预制的正确产物贯穿宿主、工具和评分器，要求文件路径与评分结果均能回放；这一步只验收环境。
2. 再加入一个刻意错误的产物，确认评分器能拒绝它，排除“任何文件都算成功”的伪通过。
3. 两项环境检查通过后才运行固定模型的小任务集，并分别记录模型失败、工具失败和环境失败。

### 进一步辨析：环境验收与能力验收需要两套样例

已知合法产物适合验证评分器线路，但不适合估计模型解决率。一个线路样例可以让智能体直接复制正确文件，仍不足以证明它会做工程推理。反过来，模型产生了看似合理的未知解，而评分器没有启动，也不能当作能力已通过。

后续验收可以分成三张独立清单：宿主能力与容器依赖、文件与工具接口、真实任务评分。前两张允许合成最小样例，第三张才要求真实任务与保留结果。每个未满足项都明确指出“阻止执行”还是“降低可比性”，避免一串绿色运行日志覆盖关键缺口。

目前不应再增加模型规模或提示词候选来绕过宿主问题。这一决定不是宣告某类 agent 无效，而是承认当前环境无法生成用于比较的证据。对一个受约束的工程项目，提前识别不可满足条件，比继续消耗推理预算更有价值。
