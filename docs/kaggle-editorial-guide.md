# Kaggle 专栏编辑约定

专栏把比赛执行记录提炼成可阅读、可追溯的技术文章。首批内容于 2026-11-26 整理，依据 `kaggle_try` 提交 `b3ddf87ddb3383e77ea7055702ff08b2c137f548` 的文档；Carvana 的预检状态另于 2026-11-26 02:07 UTC 只读核对。

## 文章结构

每个比赛保留一篇主要复盘，使用[六章写作模板](templates/kaggle-case-study.md)。主章节依次为“问题定位”“技术思路与路线”“评价方式”“结果与证据”“思考与结论”“下一步”，最后附“资料与证据”。问题定位标题可以追加本题难点；三级标题承载逐题的技术分析，不按运行日志顺序重述所有操作。

开头先给明确的核心判断，结论说明依据与适用范围。技术路线必须能从数据一路讲到最终输出，评价方式解释指标和数据角色，下一步提出有对照、确认与停止条件的试验。不能只把旧提纲换成六个标题；每一章都要回答模板中的实质问题。

表达以专业且容易理解为准：先说明对象和目的，再解释术语、机制与取舍。代码、公式和图表之后紧跟含义。写“本轮保留单模型，因为固定对照未给集成收益”，不写没有依据的口号；未实施的方案明确标识，鲜明观点与证据边界同时保留。

跨比赛文章围绕验证、指标、误差、预算等共同问题组织，链接具体案例。观点可以有明确立场，但未做消融时，不把合理解释写成已经建立的因果关系。

使用 `sample: false`，不虚构作者亲自完成训练、独立掌握技能或获得奖牌的经历。原始实验可能由工具和代理协助完成；项目证据与个人能力是不同问题。

## 新增一篇比赛复盘

文件放入 `src/content/posts/`，以 `kaggle-NN-slug.md` 命名。日期是文章发布日期，`evidenceDate` 是所引用实验／状态的记录日期。

```yaml
---
title: 比赛名称：一条有适用条件的判断
description: 用一两句话说明这篇文章值得阅读的具体问题。
date: 2026-11-26
category: Kaggle
tags: [表格学习, 验证设计]
cover: workflow
coverImage: /kaggle/18/cover.svg
coverAlt: 一句准确描述赛题对象与方法的文字
coverCaption: 原创方法插图，非官方标志或赛题样本。
sample: false
featured: false
draft: false
kaggle:
  kind: case
  number: 18
  topic: 表格学习
  status: 尚未出分
  result: 已实现验证协议，尚无官方评分
  evidenceDate: '2026-11-26'
  source: https://leebin-try.github.io/kaggle/sources/#case-18
  recordSource: https://github.com/OWNER/REPO/blob/COMMIT/TASK/docs/run.md
  competitionUrl: https://www.kaggle.com/competitions/COMPETITION
---
```

`topic` 支持 `src/config.ts` 中的六类；新增题型时同步类型校验与浏览器测试。`status` 只用“已出分”“验证受阻”“尚未出分”。已评分项目增加 `submission` 字段，并在正文准确说明指标方向、Public／Private 及来源。不得用 0 填充未知分数。

方法论文章将 `kaggle.kind` 设为 `method`，保留 `source`、`recordSource`、`evidenceDate`，无需比赛编号与评分。专栏页面、公开证据摘要、归档、RSS、搜索会从内容集合生成。

## 证据与权限

公开结果摘要是作者根据项目记录整理的说明，不是第三方独立认证。已评分应有终态回执记录；上传、开始执行、预检完成、完整产物验证与正式评分分别表述。实时补记应写明观察时间与查询范围。

原始仓库为私有时，注明访问权限，公开足以理解结论的摘要；不把私有原记录标成人人可访问的公开资料。使用精确提交链接，避免可变分支让旧结论失去出处。

不加入比赛原始数据、逐样本预测、检查点、凭据和完整运行日志。允许从已核实记录按字段白名单导出可公开的聚合训练指标、计数与对照结果；它们不能包含样本 ID、标签行、文本、图像或设备凭据。示例与推导标明为合成，不能把它们画成真实实验。

## 图像与技术深度

所有 Kaggle 文章使用逐题制作的原创封面与正文方法图；封面、正文和分享卡片保持一致。没有授权可再分发的比赛原图时，使用原创技术图，不复制官方标志或病例影像。替换通用图片不是只换颜色：图形对象与方法依赖都应对应具体题目。

实测图必须标注运行／模型、集合、指标方向、日志频率、采样与选择条件。只连接实际观察点，不平滑或补造验证值；训练与验证测量条件不同、达到轮次上限、校准复用、产物校验未完成等限制写在图旁边。柱状对照不使用误导的小范围截断夸大小差异。

生成入口：`scripts/build-kaggle-assets.py --source-root /path/to/kaggle_try`，用已有的 Python／Matplotlib 环境执行，禁止加载模型和原始样本。脚本产出原创 SVG、白名单指标 CSV 与 `src/data/kaggle-figures.json`／`public/kaggle/figures.json`；两份清单必须一致。`node scripts/render-kaggle-covers.mjs` 从 SVG 渲染分享 PNG。需要 Chrome 时可用 `CHROME_EXECUTABLE` 指定路径。

正文围绕问题定义、具体实现、可手工核对的例子、实验对照、失效条件和下一步设计展开。数量、字数和图片数只用于防止退回提纲，不代替技术审阅。未完成的项目保留真实工程缺口，不为凑图伪造训练曲线。

## 信息密度与阅读排版

正文保持至少 16px，行高约 1.8，段间距约 0.8em；二级标题前后约 28px／12px，三级标题约 20px／8px。依靠减少留白和明确层级提高密度，不缩小正文来挤内容。正文最大宽度约 760px，长代码与宽表在容器内横向滚动。

按最新阅读要求，文章封面恢复独占整行，保持原图比例，桌面最高约 480px；列表封面也占据卡片整行。正文仍使用紧凑间距。实测图保持比例、坐标轴和文字完整，可点击放大，不裁掉标签、不拉伸图片。桌面目录位于左侧并随滚动固定，当前章节高亮；窄屏使用可展开目录，保留键盘与原生锚点跳转。

## 中英文维护

网站默认英文，中文使用 `/zh/` 路由。每篇文章保留同名的中英文版本，英文正文放在 `src/content/posts/en/` 并声明 `lang: en`。具体规则见[双语维护说明](bilingual-editing.md)和[英文写作模板](templates/kaggle-case-study.en.md)。两种语言的分数、状态、来源、章节结构与图表保持对应；翻译已有报告不代表重新开展文献核验。

## 发布检查

运行 `npm run typecheck`、`npm run build` 与 `npm run test:e2e`。浏览器检查包含桌面／手机分类、分享链接、状态标注、搜索、RSS 与主题。构建产物还要检查专栏内部链接、证据锚点、内容数量以及旧页面是否保留。

推送 `main` 后由现有 GitHub Actions 发布，确认工作流终态及线上 URL。推送成功与部署成功分别报告，不把本地预览称作已经上线。
